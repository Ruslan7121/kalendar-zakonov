# Рефакторинг `src/canvas.tsx`: план и состояние

Составлен 22.11.2026. Сайт, данные и тексты при рефакторинге не меняются: после каждого шага `data/*.json` совпадают с эталоном побайтно, все тесты (`npm test`, включая WebKit) зелёные.

## Как устроен файл сейчас

`src/canvas.tsx` — один файл около 2,3 МБ. Это одновременно:

| Что | Размер | Кто его трогает |
|---|---|---|
| **Данные** — около 30 больших констант (`DATA`, `CAL`, `BP`, `ORG`, `ORGX`, `ZTAG`, `TRACK`, `LAWS`, …) | примерно 1,46 МБ (62%) | конвейер: `pipeline/collect/*`, `pipeline/merge/*` через `pipeline/lib/common.py` (`get_block`, `set_block`, `write_canvas`) |
| **Интерфейс, зависящий от данных** — компоненты и функции, которые читают константы данных напрямую или через другие функции | примерно 0,63 МБ (141 оператор) | разработчик интерфейса |
| **Интерфейс, не зависящий от данных** — тема, ссылки, фильтры, период, элементы карточек | примерно 0,16 МБ | разработчик интерфейса |

Конвейер и тесты **разбирают текст** `canvas.tsx` по регулярным выражениям и меткам `/* ИМЯ:start */ … /* ИМЯ:end */`:
`pipeline/lib/common.py`, `pipeline/merge/split_data.mjs` (строгие правки с проверкой «найдено ровно N раз»), `auto_ztag.py` (читает `ZW/ZT/ZC/AUTOZ`),
`ztag_merge.py`, `orgx_merge.py`, `bp_merge.py`, `cal_merge.py`, `peek.py` и около 20 тестов (`tests/js/load_canvas.mjs` собирает файл через esbuild и обращается к внутренним именам).
Поэтому любое перемещение данных или кода, на который опираются эти разборщики, требует одновременной правки конвейера.

## Что сделано (безопасная часть)

Из `src/canvas.tsx` вынесен код интерфейса, **который не зависит от данных** (проверено разбором дерева кода TypeScript: оператор переносится, только если он не обращается ни к одной константе данных, ни прямо, ни через другие операторы, не изменяется извне (`let`) и на него не опираются блоки данных и разборщики конвейера).
Вынесено 192 оператора в `src/ui/`:

| Модуль | Что внутри |
|---|---|
| `theme.tsx` | палитры светлой и тёмной темы, цвета, общие стили (`css`, `card`) |
| `telegram.tsx` | интеграция с Telegram, «Поделиться», адрес службы уведомлений |
| `loader.tsx` | подписка компонентов на загрузку данных по месяцам |
| `nv.tsx` | базовые элементы карточек и окон (`NvModal`, кольца, плитки) |
| `sv.tsx` | блоки окна законопроекта |
| `orgs.tsx` | работа госорганов: период (`PeriodHead`), документы, новости, пустые состояния |
| `filters.tsx` | фильтры органов и меток, «Мои интересы», избранное |
| `laws.tsx` | идентификаторы и ссылки законов «Вступают в силу» |
| `misc.tsx` | даты, форматирование, мелкие функции и константы |

`src/canvas.tsx` подключает их обычными `import … from './ui/…'`. Что подправлено вокруг:
- `pipeline/merge/split_data.mjs`: в `web/gen/app.tsx` пути `./ui/…` переписываются на `../../src/ui/…`; текст модулей учитывается при выборе «общих» записей данных (иначе номера, упомянутые только в вынесенном коде, переехали бы между `core.json` и месячными файлами);
- тесты, читающие код как текст, читают и `src/ui/*` (`test_share_link`, `test_calendar_visible`).

Оставлены в `canvas.tsx` намеренно: загрузчик `GDX` (его ищет `split_data.mjs`), словари `ZW/ZT/ZC/ZG/AUTOZ` (их читает `auto_ztag.py` и `ztag_merge.py`), `ORGN`, `ORG_HIDE_FROM`, `isResDoc` (на них опираются разборщики и тесты).

## Что не сделано и почему: данные в отдельный файл

Цель — `src/data.ts` (или только `data/*.json`) как единственный источник данных, а `src/canvas.tsx` и `src/ui/*` — только интерфейс. Сейчас этого нет:

1. **Интерфейс читает данные как глобальные константы.** Около 80% кода интерфейса (141 оператор: `Calendar`, `CalendarApp`, `Itogi`, `Panel`, `NewsFeed`, `OrgMap`, …) прямо или косвенно обращается к `DATA`, `CAL`, `BP`, `ORG` и другим. Вынести их в модули можно, только когда данные станут явным импортом (`import { BP, ZTAG } from './data'`).
2. **Конвейер правит текст файла с данными.** Все скрипты ищут блоки в `src/canvas.tsx` (`CANVAS`). Файл данных должен остаться таким же по форме или конвейер нужно перенастроить на другой путь целиком.
3. **Данные поддерживаются слиянием «код + данные».** В `canvas.tsx` есть операторы, которые при загрузке сливают источники (`CAL.p ∪ DATA`, `ORGX → ORG`, `INIC → INFO`, `LAWS_FIX → LAWS`, `SFI → ORG`). `split_data.mjs` вырезает их и подменяет на загрузчик `GDX`. Их надо вынести в отдельный модуль слияния, который выполняется и в Node (для `split_data`), и в браузере.
4. **Тесты и `split_data.mjs` держатся за текст.** Правки `split_data.mjs` требуют «ровно N совпадений» и упадут при любом сдвиге; `loadCanvas` собирает один файл с внутренними именами.

### Порядок работ для полного разделения (каждый шаг проверяется: `data/*.json` и сайт совпадают, тесты зелёные)

1. Завести `src/data.ts`: перенести туда блоки данных вместе с метками `/* ИМЯ:start */`; `CANVAS` в `pipeline/lib/common.py` и `split_data.mjs` указывает на него. `canvas.tsx` получает `import { DATA, CAL, … } from './data'`.
2. Переписать `split_data.mjs` так, чтобы он работал с `data.ts` (значения берёт выполнением модуля, как сейчас через `evalCanvas`), а в `web/gen` подставлял `import … from 'gdx'` вместо `./data`.
3. Вынести операторы слияния (пункт 3 выше) в `src/data-merge.ts`.
4. Перенести оставшиеся компоненты в `src/ui/*` по одному, начиная с самых «листовых» (`Itogi`, `NewsFeed`, `OrgMap`), с импортом данных.
5. Обновить тесты (`loadCanvas`) и разборщики (`auto_ztag.py` и др.) на новые пути.

Оценка: от нескольких дней работы; рекомендуется выполнять отдельным этапом и только при необходимости (сайт и конвейер работают и без этого).
